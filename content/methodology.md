# Методика AI-SDLC: конспект документации

Плотный конспект документа «Целевая методика AI-native SDLC» (пространство **SSD / «ДПР»** на `wiki.office.msk.mtt`): принципы, целевая операционная модель, SDD-ядро, стадии (plays), governance, измерение и управление переходом. Конспект сохраняет названия разделов, терминологию, цифры и структуру таблиц исходных страниц; ссылки на источники — в конце каждого раздела.

**Паспорт документа:** редакция **1.1** · дата **2026-10-28** · статус: **целевая методика**.

> **Как читать.** Это описание **целевой модели**, к которой мы идём; адопшн — поэтапный, **волнами**. Принятые решения стабильны. Детали реализации с пометкой `калибруется в Фазе 0` уточняются по её данным.

Методика **вендор-нейтральна**: описывает роли, контракты и контроль, а не конкретный продукт.

Методика перестраивает SDLC в конвейер из **5 стадий** с обратными связями (Plan → Design → Build → Test → Deploy): агент выполняет черновую работу, человек утверждает результат на явных точках контроля (gate). Каждая стадия оставляет версионируемый артефакт (`intent.md → spec.md → tasks.md → diff+tests → MR`); старт — под контролем человека, автономия расширяется по мере созревания контроля (**rules → skills → hooks → evals**) и по метрикам.

Внедрение поэтапное, начиная с общего фундамента. Успех измеряется в двух слоях: наверху **метрики потока** (время «идея → прод», стоимость на фичу, доля дефектов в проде), **DORA** и **AI-специфичные** — операционные.

**Узкое место смещается с написания кода на проверку и приёмку результата** — отсюда упор методики на верификацию, управление контекстом и governance.

## Часть 0. Executive summary

### 0.1 Что предлагается

Методика описывает управляемый поток изменения от замысла до релиза, в котором человек и агент работают на разных ролях: люди инициируют, направляют и утверждают на gate, агент исполняет стадии.

Схема потока (из исходной страницы, блок `code` language=none):

```text
      ┌──────────── люди: инициируют, направляют, утверждают на gate ────────────┐
      │                                                                          │
      ▼                                                                          │
   ┌──────┐   ┌────────┐   ┌───────┐   ┌──────┐   ┌────────┐                     │
   │ PLAN │──▶│ DESIGN │──▶│ BUILD │──▶│ TEST │──▶│ DEPLOY │─── релиз ───────────┘
   └──────┘   └────────┘   └───────┘   └──────┘   └────────┘
   intent.md   spec.md      tasks.md   tests+evals  MR + ревью
   (вход)      (OpenSpec)              (самопро-    + gate
                                        верка)
```

Ключевые свойства потока, зафиксированные на схеме:

- на стыке стадий — **точка контроля человеком (gate)** и **детерминированный hook**;
- каждый артефакт версионируется в git → **цепочка коммитов = аудиторский след**;
- **MAINTAIN** (автономная эксплуатация, замыкание петли) — будущая фаза, **вне текущего охвата**.

Артефакты по стадиям: `intent.md` (вход) → `spec.md` (OpenSpec) → `tasks.md` → `tests + evals` (самопроверка) → `MR + ревью + gate`.

### 0.2 Охват

- Процесс описывает **новые фичи над текущим Exolve** и **новые продукты**.
- Создание контекста — **reverse-spec по легаси-сервисам** и наполнение `product-context/` — это **отдельный bootstrap-процесс**, а не часть потока одного изменения (§2.6, §3.8).
- **Прод-инциденты в процесс не входят.**

## Часть 1. Главные принципы (фундамент)

Девять принципов, на которых держится вся методика:

| # | Принцип | Что означает на практике |
| --- | --- | --- |
| 1 | **Артефакт — истина и аудит** | Каждая стадия заканчивается версионируемым артефактом, который читает следующая. Цепочка коммитов отвечает на вопрос «кто что просил, что агент сделал, кто утвердил» |
| 2 | **Человек отвечает за суждение** | Агент готовит черновик; решение, требующее суждения (что построить, что смержить, что задеплоить), принимает и подписывает человек |
| 3 | **Верификация важнее генерации** | Ценность не в том, что агент пишет код, а в том, что результату можно доверять. Каждый агент обязан иметь способ проверить свою работу до того, как её увидит человек |
| 4 | **Контекст — ограниченный ресурс** | Знания загружаются точечно (just-in-time), а не «всё всем». Раздутый контекст ухудшает результат и стоит токенов |
| 5 | **Одно правило — одно место** | Факт живёт в одном файле, остальные ссылаются. Процедуры (skills) ≠ знания (rules/context) ≠ контракт (proto/spec). Дублирование расходится и устаревает |
| 6 | **Спека первична (SDD)** | Спецификация — первичный артефакт для любого изменения; код и тесты производны от неё. Объём спеки пропорционален изменению |
| 7 | **Детерминизм там, где нельзя ошибаться** | Правило-подсказка (skill) делает нарушение редким; детерминированная проверка (hook) делает его почти невозможным. Всё, что должно держаться всегда, оборачивается в hook, а не только промптом |
| 8 | **Вендор-нейтральность** | Методика описывает роли и контракты, а не продукт. Модель и харнесс — сменяемые компоненты за слоем абстракции |
| 9 | **Автономия увеличивается через зрелость** | Переход от подсказки к автономии происходит по метрикам, а не по дате. Автономия без созревших hook и evals не включается |

## Часть 2. Целевая операционная модель

Сводная схема целевого сетапа (из исходной страницы):

```text
КОНВЕЙЕР: Plan → Design → Build → Test → Deploy
          intent   spec   tasks   diff   MR
Рамка всего — ЛЮДИ И ПРОЦЕСС (команда-платформа · управление изменениями · Agile Lead)
обратная связь [ Верификация: самопроверка · evals · приёмка AQA ] [ Метрики: бизнес + DORA/AI ]
──────────────────────────────────────────────────────────────────────────────────────────────────
ядро конвейера [ Межсервисная доставка и релиз: публичный сервис + сервисы · 2 режима ]
(снизу вверх)   [ SDD-ядро в Git: OpenSpec · polyrepo · 2 гейта · CODEOWNERS ]
                [ LLM и агенты (L1/L2/L3): Enterprise-доступ + LLM-прокси (шлюз) · opencode · роли ]
──────────────────────────────────────────────────────────────────────────────────────────────────
ограждения      КОНТРОЛИ по жёсткости: правила/контекст → skills → hooks → платформа → gate (человек)
(поперёк всего) + периметр данных, kill-switch
```

### 2.1 Конвейер AI-SDLC

Пять стадий образуют конвейер с обратными связями. Каждая производит артефакт, который запускает следующую:

| Стадия | Входной артефакт | Выходной артефакт | Что фиксирует |
| --- | --- | --- | --- |
| Plan | идея / тикет | `intent.md` | что хотим, зачем, при каких ограничениях |
| Design | `intent.md` | бизнес-спека (`proposal`+`specs`, репозиторий продукта) → decompose → изменение сервиса (`proposal`+`specs`+`design`+`tasks`) в репозиториях сервисов | требования + дизайн + отмеченные зоны риска (SDD-ядро) |
| Build | `design`+`tasks` | `tasks.md` (раздел «План реализации») + diff | код-обоснованный план → код |
| Test | diff + `tasks.md` | тесты + результаты evals | доказательство корректности |
| Deploy | зелёный MR | находки ревью (в MR) → merge → запись релиза и архивация изменения | ревью, gate, выкатка |

### 2.2 Вендор-нейтральная агентная архитектура

> *Калибруется в Фазе 0: конкретный субстрат — модель (L1) и харнесс (L2).*

Строим слой абстракции, без привязки к продукту. Три уровня:

```text
┌─────────────────────────────────────────────────────────────┐
│ L3. РОЛИ АГЕНТОВ                                            │
│ orchestrator · spec · coder · reviewer · etc                │
├─────────────────────────────────────────────────────────────┤
│ L2. ХАРНЕСС (сменяемый)                                     │
│ opencode / собственный оркестратор / Claude Code / …        │
│ единый интерфейс: prompt, tools, hooks, permissions, logs   │
├─────────────────────────────────────────────────────────────┤
│ L1. МОДЕЛЬ (сменяемая, внешний API — Enterprise-решение)    │
└─────────────────────────────────────────────────────────────┘
```

- **L1 — модель.** То, что отвечает на запрос. Сменяемый компонент: выбирается под задачу. К контрактам и evals не привязана — провайдера можно заменить, не переписывая роли.
- **L2 — харнесс.** Оболочка, в которой работает агент: запускает модель, даёт ей инструменты, перехватывает вызовы (hooks, permissions), пишет логи. Здесь технически реализуется часть контролей. Сменяемый: opencode сегодня, Claude Code потенциально позже — при смене меняется только этот уровень.
- **L3 — роли агентов.** Контракты «кто за что отвечает и чем ограничен». От модели и харнесса не зависят.

**Переносимость между харнессами.** Смена харнесса меняет только уровень L2, но skills, hooks и rules не считаются переносимыми без проверки: набор возможностей у инструментов разный (skills, rules, hooks, permissions). Смена харнесса требует прогона evals на нём (§4.4).

**Критерии выбора харнесса:** поддержка skills, hooks и permissions; работа через шлюз; возможность серверного развёртывания; поддержка нескольких провайдеров моделей.

**Доступ к модели и ключи.** На границе L2↔L1 стоит внутренний **шлюз** (gateway/proxy). Доступ организационный, не персональный:

- **идентичность — на человека** (корпоративный SSO): нужна для атрибуции действий и токен-бюджетов; **сырой API-ключ разработчику не выдаётся**;
- **ключи — пул из единиц, не по числу людей**: сегментация по границам риска и учёта — интерактивная разработка (1 пул) · CI по окружениям (dev/staging/prod) · служебный ключ для батч-агентов (reverse-spec). Порядок — **~3–6 ключей, не 15 и не 130**;
- **харнесс ходит на endpoint шлюза** (переопределение base URL) с короткоживущим токеном по SSO — **сырой провайдерский ключ не покидает платформу**;
- **шлюз — единая точка kill-switch и токен-бюджетов**: централизованный отзыв/ротация ключей и лимиты по командам; меньше ключей + одна точка = меньше поверхности атаки.

Это согласует организационный доступ с «действие привязано к человеку»: идентичность — на человека, секрет — централизован. Раздача сырых ключей по людям сломала бы организационный доступ, kill-switch и периметр.

**Роли агентов** (минимальный набор на 5 стадий):

| Роль | Стадии | Что делает | Чем ограничена |
| --- | --- | --- | --- |
| **orchestrator** | все | маршрутизирует задачу, вызывает роли; знаниями сам не владеет — их подтягивает исполнитель по месту | не пишет в базу знаний |
| **spec** | Plan, Design; в репозитории сервиса — полный цикл | в репозитории продукта разворачивает intent в бизнес-спеку (`proposal` + `specs`) по схеме `business`; в репозитории сервиса ведёт полный цикл OpenSpec (explore → proposal → apply) и артефакты `proposal`, `specs`, `design`, `tasks`; decompose — его скилл; читает `product-context/` по индексу за доменными фактами | в продукте не пишет код и не создаёт `design`/`tasks`; открытые вопросы формулирует, но не отвечает на них сам |
| **coder** | Build | по `tasks.md` пишет код и тесты; читает правила и контекст репозитория | не мержит; не трогает защищённые пути (hook) |
| **reviewer** | Test, Deploy | ревьюит MR против политики (`REVIEW.md`), сверяет с spec и tasks; в Go-сервисах проверяет и качество кода | находки не утверждают MR — утверждает владелец кода через защиту веток |

**Два режима spec-агента.** В репозитории продукта `spec` работает от `intent` PM/PO и создаёт только бизнес-спеку: `proposal` + `specs` по схеме `business`, без `design` и `tasks`. В репозитории сервиса он ведёт полный цикл OpenSpec (`explore → proposal → apply → …`): дельта сервисной спеки, `design`, `tasks` и реализация. Decompose — скилл `spec`-агента: после Гейта 1 он раскладывает принятую бизнес-спеку на изменения в сервисах.

**Где живут знания:**

- **Правила / контекст репозитория** (аналог `CLAUDE.md`): конвенции, команды сборки и тестов, архитектура, частые ошибки. Один файл в корне репозитория, ревьюится как код, до одной страницы, читается в начале сессии.
- **Skills**: обязательные правила организации для единообразного применения (стандарт безопасности, API-конвенции). Триггерятся по описанию, версионируются, обновляются централизованно. **Доставляются серверным сервисом платформы:** локальная копия и правка запрещены, разработчик подключается тонким клиентом и не выбирает и не правит skills вручную.
- **Контекст по месту (just-in-time)**: доменные факты — выборочно по индексу, не «всё всем».

### 2.3 Слои контроля

Контроль выстроен по возрастанию жёсткости; каждый следующий подпирает предыдущий:

| Слой | Тип | Где реализуется | Пример | Что даёт |
| --- | --- | --- | --- | --- |
| **Правила / контекст** | пассивный | L3 (роли читают) | контекст репозитория, конвенции | агент знает, как надо |
| **Skills** | подсказка | L3 (роли применяют) | skill проверки безопасности API | нарушение становится редким |
| **Hooks** | детерминированный | L2 (харнесс) | блок правки защищённого пути; gate релиза | нарушение почти невозможно |
| **Настройки платформы** | неотключаемый | L2 / платформа | permissions, sandbox — задаёт платформа | инженер не может ослабить правила |
| **Точка контроля человеком (gate)** | суждение | вне стека агента | утверждение спеки, merge, авторизация релиза | ответственность на человеке |

В отрасли построение этого слоя вокруг агента — ограничений, инструментов, контуров обратной связи и проверок — называют **harness engineering**. Инструкции агенту (правила, skills) — пожелания; гарантии дают детерминированные слои: hooks, настройки платформы и проверки в CI.

### 2.4 Источник истины и легаси-системы

Новые `.md`-артефакты (intent, spec, plan) дублируют сведения, которые уже лежат в системах: задачи — в Jira, тест-кейсы — в TestIT, код — в GitLab. Если одно и то же хранится в двух местах, копии со временем расходятся. Поэтому для каждого типа артефакта — **одно авторитетное место («источник истины»), остальные на него ссылаются.**

Принятая раскладка:

- **Требования — репозиторий** (`openspec/specs/`), версионируются с кодом; Jira → трекер задач.
- **Тест-кейсы — TestIT** (агент пишет и обновляет через коннектор; тест-документация — целевой артефакт), связка по `R-id` с требованиями.
- **Перекрёстные ссылки:** у каждого `.md` — ID записи в Jira/TestIT, у каждой записи — SHA коммита.
- Изменение требования через «разницу требований» (§3.1) **помечает связанные тест-кейсы TestIT на регенерацию/ревью**, коннектор пишет обновление обратно.

### 2.5 Периметр данных и чувствительные данные

Self-hosted-моделей нет, поэтому **весь обмен с моделью идёт через внешний API**. Отсюда два разных класса данных и два разных решения.

**Инженерные артефакты — код, US, proto, spec, план, тест-кейсы.** Они нужны агенту для работы и покидают периметр при каждом вызове. Что делаем для снижения: классифицируем репозитории (какие вообще допустимо отправлять во внешний API); используем Enterprise-решение (Enterprise/Business-тариф + организационные API-ключи), где ввод/вывод по умолчанию не идёт в обучение и есть зона хранения; ограничиваем набор доступных агенту инструментов и его исходящий трафик.

**Данные клиентов — ПДн абонентов, содержимое и метаданные звонков и сообщений, тайна связи, биллинг.** Для разработки они агенту не нужны: он работает с кодом и спецификациями, а не с продакшн-данными. Правило: такие данные **не попадают в контекст агента вообще.** Что делаем:

- в тест-данных и фикстурах — только синтетика или обезличенные значения; реальные абонентские данные в US, промптах и тестах запрещены;
- перед отправкой во внешний API diff проходит проверку на секреты и ПДн (pre-commit / CI hook); нашли — блокируем;
- логи и трейсы, прикладываемые к задаче, маскируем;
- если задача действительно требует чувствительных данных — она не отдаётся агенту и остаётся ручной, пока не появится контур с моделью внутри периметра.

### 2.6 Продуктовый (доменный) контекст

**Продуктовый контекст** — **сквозное доменное знание** (термины, типы клиентов, статусные модели, интеграции, правила тарификации и т.д.), не привязанное к одному сервису; читает любой агент на любой стадии, чтобы не галлюцинировать бизнес-факты и не переоткрывать их в каждой сессии.

**Расположение.** `product-context/`.
**Структура.** `product-context/INDEX.md` (однострочные описания файлов) + доменные файлы, нарезанные по границам того, что реально нужно агентам, а не по структуре вики. Стартовый набор адаптируется под продукт — например: `glossary.md`, `client-types.md`, `lifecycle.md`, `integrations.md`, `billing-rules.md`.

**Формат файла** — frontmatter (`name`, `description`, `updated`, `owner`) + факты с обязательным источником:

```markdown
---
name: client-types
description: Типы клиентов — права доступа, ограничения операций
updated: 2026-09-04
owner: <владелец домена>
---
## Матрица прав
| Операция | Тип A | Тип B | Источник |
|---|---|---|---|
| ... | ✅ | ❌ | US EXOLVE-123 |
```

Факт без источника (US, Confluence, подтверждение эксперта) не должен попадать в файл.

**Наполнение — три источника, в указанном порядке:**

1. **Jira, разово на старте.** Агент прогоняет историю US, извлекает факты с `source: EXOLVE-XXX`.
2. **Confluence, разово на старте.** Агент прогоняет пространства, привязанные к продукту, извлекает факты с пометкой «задокументированное намерение, не проверенное поведение» — Confluence может быть устаревшим.
3. **Ручное закрытие пробелов, постоянно.** Там, где после первых двух шагов остаются явные пробелы, продукт закрывает их через тот же интервью: агент задаёт вопросы, оформляет файл, — целевой артефакт `product-context/*.md` вместо `intent.md`.

Продукт валидирует черновик из всех трёх источников целиком, только после этого — коммит.

**Порядок наполнения зависит от пути.** Тяжёлый разовый прогон Jira/Confluence (шаги 1–2) — действие, требуемое прежде всего под путь **transform**. Поэтому в Фазе 0 и на greenfield-пути продуктовый контекст стартует **тонким** — глоссарий плюс то, что реально нужно пилоту, — набираемым через интервью Plan. Полный скан двух источников подключается вместе с transform-путём.

**Загрузка — прогрессивная, через индекс**: агент читает `INDEX.md`, выбирает 1–3 релевантных файла под задачу, не грузит слой целиком.

**Пополнение дальше.** Каждая новая принятая `spec.md` — потенциальный источник нового доменного факта: если в ней всплыло что-то за рамками одного изменения, факт выносится в `product-context/`. Открытые вопросы и допущения из `intent.md`/`spec.md`, закрытые ответом продукта, конвертируются в факты того же слоя тем же порядком.

**Правило наполнения.** «Агент ошибся дважды → правка в контекст репозитория или skill»: повторная ошибка агента на одном и том же становится правкой контекста, а не разовым исправлением.

**Владелец.** Продукт/аналитик — по домену; факт меняется через обычный MR в репозитории.

### 2.7 Масштабирование контекста

Два слоя знаний масштабируются по-разному и индексируются **разными механизмами**:

| | Продуктовый (доменный) контекст (§2.6) | Контекст репозитория (§2.2) |
| --- | --- | --- |
| Что содержит | сквозные доменные факты (термины, статусы, тарифы) | репо-конвенции, команды сборки/тестов, архитектура, грабли |
| Индексируется | **по релевантности** — `INDEX.md`, агент выбирает 1–3 файла по теме | **по локальности** — файловая иерархия; грузится контекст того места, где идёт работа |
| Форма | библиотека доменных файлов + `INDEX.md` | корневой one-pager (≤1 стр.) + локальные `CONTEXT.md` по сервисам |
| Как грузится | прогрессивно по индексу, не весь слой | по месту: корневой + локальный для текущего каталога |

**Масштабирование:** с ростом системы растёт **общее** знание, но не всегда-загружаемый файл — рост уходит в just-in-time и декомпозированные слои (больше доменных файлов под `INDEX.md`; больше локальных `CONTEXT.md` по сервисам), которые грузятся выборочно; корневой всегда-загружаемый контекст остаётся тонким. Примеры файлов — Приложение G.

## Часть 3. SDD как ядро методики

### 3.1 Что даёт

1. **Определённый вход.** Спецификация — единая точка. Неопределённость выявляется и снята до генерации.
2. **Трассируемость.** Цепочка требование → тест-кейс → код → автотест становится проверяемой, а не «на глаз». Итоговый артефакт — матрица покрытия (требования × тест-кейсы × код) генерируется автоматом.
3. **Управляемые изменения.** Изменилось требование — не переделываем всё: считаем, что именно поменялось («разница требований»), и перегенерируем только затронутые код и ТК. Нетронутое (и ручные правки в нём) остаётся целым.

### 3.2 Фреймворк — OpenSpec

Фреймворк SDD — **OpenSpec**: вендор-нейтрален (работает с 30+ инструментами, не требует своих API-ключей), имеет плагин под opencode.

Правила использования:

- Модель артефактов OpenSpec: каждое изменение — отдельная папка `changes/<id>/` с `proposal`, `specs`, `design`, `tasks`; принятые изменения уходят в архив. Разделение `specs/` (текущая истина) и `changes/` (предложения) даёт встроенную **разницу требований** — руками её строить не нужно.

Соответствие артефактов OpenSpec конвейеру (два уровня):

| Уровень | Наш артефакт | OpenSpec | Владелец |
| --- | --- | --- | --- |
| Бизнес (репозиторий продукта) | intent (запрос на изменение) | `proposal` | продукт |
| Бизнес (репозиторий продукта) | бизнес-требования | `specs` | продукт |
| Сервис (репозиторий сервиса) | задача сервиса | `proposal` | инженер |
| Сервис (репозиторий сервиса) | требования к сервису (дельта сервисной спеки) | `specs` | инженер |
| Сервис (репозиторий сервиса) | техдизайн | `design` | инженер |
| Сервис (репозиторий сервиса) | нарезка на задачи + план реализации | `tasks` | инженер |

**Шаг decompose.** После Гейта 1 бизнес-спека лежит в репозитории продукта, а в репозиториях затронутых сервисов создаётся изменение сервиса: `changes/<id>/` с четырьмя артефактами (`proposal`, `specs`, `design`, `tasks`). Переход делает скилл decompose `spec`-агента:

- запускает **интегратор фичи** — команда публичного сервиса, а если сервис один, его команда (§3.11);
- агент предлагает список затронутых сервисов; интегратор подтверждает его до того, как что-либо создаётся;
- затем агент открывает в репозитории каждого сервиса MR с заготовкой изменения: `proposal` сервиса со ссылкой на бизнес-спеку и feature R-id (что именно меняется в этом сервисе); дальше команда сервиса дорабатывает `specs` (дельту сервисной спеки), `design` и `tasks` в репозитории сервиса, где есть код и контекст; explore/propose заново не выполняются — изменение пришло от продуктового `proposal` по зависимости. Технических деталей сервисов бизнес-спека не содержит;
- ревью MR маршрутизирует CODEOWNERS (§4.0); приёмка изменения сервиса целиком — Гейт 2.

Пропозал и бизнес-спека (`proposal` + `specs`) живут в репозитории продукта. От них **через зависимость** открывается изменение в репозитории сервиса с четырьмя артефактами (`proposal`, `specs`, `design`, `tasks`) по этому продуктовому изменению. В репозитории сервиса **explore и proposal заново не выполняются** — `proposal` сервиса наследуется из продуктового (ссылка на бизнес-спеку + feature R-id); команда дорабатывает `specs` (дельту сервисной спеки), `design` и `tasks` под свой сервис.

`tasks` — **двухсостояный артефакт**: на Design это нарезка на задачи (уровень подхода, утверждается на **Гейте 2**); на Build тот же файл дополняется разделом **«План реализации»** — код-обоснованной привязкой к реальному коду (какие файлы, порядок, риски, чем доказываем; §4.3). Отдельного `plan.md` нет — план реализации живёт внутри `tasks.md`.

### 3.3 Нотация — формат OpenSpec: требования и сценарии

Требования и критерии приёмки пишутся в формате, который разбирает и проверяет OpenSpec (`openspec validate --strict`); отдельной нотации поверх него нет. Шаблон — Прил. B.

- **Требование** — блок `### Requirement: <название>`. Первая строка под заголовком — нормативная фраза с `SHALL` или `MUST` (латиница, заглавные): валидатор ищет это слово именно в первой строке. Следом — `id: R-<n>` и обязательный `source:`.
- **Сценарий** — критерий приёмки: блок `#### Scenario: <название>` (ровно четыре `#`) со строками `- **GIVEN**`, `- **WHEN**`, `- **THEN**`. У каждого требования минимум один сценарий: правило «одно требование — минимум один тест».
- **Дельта изменения** — разделы `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`; после архивации изменения требования попадают в `openspec/specs/<capability>/spec.md`.

### 3.4 Истина требований — репозиторий

Источник истины требований — репозиторий (`openspec/specs/`; раскладка — Прил. G.4). Следствие: **Jira перестаёт быть хранилищем требований и становится трекером задач и статусов** — тикет ссылается на спеку, но не содержит её.

Чтобы продукт не работал с git напрямую, он пишет в репозиторий через удобную обёртку (например Opencode Desktop); репозиторий при этом остаётся истиной.

### 3.5 Разделение владения и два гейта

Черновик всех артефактов пишет агент. Владение и утверждение — человеческие и **разные на двух слоях**:

| Слой | Артефакты OpenSpec | Владелец (источник + утверждает) | Нотация |
| --- | --- | --- | --- |
| Бизнес: «что и зачем» | `proposal` + `specs` — **бизнес-спека** | продукт (PO / аналитик) | требования и сценарии OpenSpec, много примеров |
| Технический: «как» | **изменение сервиса**: `proposal` + `specs` (дельта сервисной спеки) + `design` + `tasks`; поведение сервиса фиксирует **сервисная спека** (`openspec/specs/<сервис>`) | инженер | требования и сценарии OpenSpec, строже + ссылки на proto |

**Два вида спеки.** Бизнес-спека — бизнес-требования к фиче на уровне продукта (`proposal` + `specs`); сервисная спека — текущее поведение и контракты одного сервиса, лежит в репозитории сервиса.

Из разделения следуют **два гейта**, а не один:

- **Гейт 1 (бизнес-приёмка).** Продукт принимает бизнес-требования. Это вход в техдизайн.
- **Гейт 2 (техническая приёмка).** Инженер принимает изменение сервиса целиком (`proposal`, `specs`, `design`, `tasks`). Это вход в Build.

**Связь бизнес-спеки и техдизайна.** На переходе от бизнес-требований к техдизайну легко потерять смысл. Чтобы этого не было: каждый элемент техдизайна ссылается на конкретное бизнес-требование (R-id); если бизнес-требование, US и proto противоречат друг другу, агент останавливается и задаёт вопрос владельцу, а не выбирает вариант сам.

**Владельцы и CODEOWNERS.** Кого спрашивают на гейте, решает CODEOWNERS по пути файла (§4.0). Принципы ведения:

- в файле стоят **группы GitLab команд**, а не люди: кадровые изменения вносятся в состав группы, ответственный — лид команды;
- в каждом файле обязательна **строка владельца по умолчанию**, чтобы у любого пути был владелец;
- принудительность обеспечивает **защита веток**: аппрув код-оунера обязателен (§4.5);
- актуальность держит **аудит по расписанию**: он находит репозитории без CODEOWNERS, с пустыми или несуществующими группами и выдаёт отчёт платформе.

Механизм раскатки шаблонов — TBD (§3.12).

### 3.6 SDD применяется ко всем изменениям

Через спеку проходит **любое** изменение. **Объём спеки пропорционален изменению**: тривиальное (добавить поле, поправить лог) — 1–2 требования и один сценарий, агент генерирует быстро, человек утверждает без углублённого разбора; нетривиальное — полная спека с дизайном и разбором противоречий.

**Спека-артефакт — для всех; продуктовый гейт — не для всех.** Требование «спека на любое изменение» держит трассируемость, но не означает, что каждое изменение проходит через приёмку продуктологов. Поэтому класс изменения решает, нужен ли Гейт 1:

- **Меняется внешне наблюдаемое бизнес-поведение** (новое поле в ответе, новое правило тарификации) → Гейт 1 продуктологов обязателен. Изменение `proto` / публичного контракта — автоматический триггер Гейта 1.
- **Нет внешне наблюдаемого изменения** (рефакторинг, внутренний техдолг, логи, производительность) → спека остаётся, но `proposal` + `specs` владеет и принимает **инженер**; продуктовый гейт не нужен. Здесь Гейт 2 (техприёмка) — единственный. В OpenSpec маленькое изменение — это маленькая папка `changes/<id>/`.

Пример минимальной спеки:

```text
proposal: добавить булево поле `call_record` в объект `attributes` ответа GetAttributes
specs:
## ADDED Requirements
### Requirement: Признак записи разговоров в атрибутах номера
Система SHALL возвращать в объекте `attributes` ответа POST /number/v1/GetAttributes булево поле `call_record`.
id: R-1
source: proposal
#### Scenario: Запись разговоров выключена
- **GIVEN** номер существует и запись разговоров выключена
- **WHEN** вызван POST https://api.exolve.ru/number/v1/GetAttributes с body {"number_code": "<code>"}
- **THEN** ответ 200, attributes.call_record = false
#### Scenario: Запись разговоров включена
- **GIVEN** номер существует и запись разговоров включена
- **WHEN** тот же вызов
- **THEN** ответ 200, attributes.call_record = true
```

### 3.7 Поток для нового кода (greenfield)

`intent` → бизнес-спека (продукт, **гейт 1**) → техдизайн + `tasks` (инженер, **гейт 2**) → Build.

### 3.8 Поток для легаси (reverse-spec)

> *Калибруется в Фазе 0: жизнеспособность reverse-spec вширь (go/no-go на образце).*

Агент не может безопасно менять код, поведение которого нигде не описано. Поэтому для легаси сначала нужно снять **baseline** — спеку «как есть» поверх существующего сервиса, — и только потом менять. Baseline — это поведение одного сервиса под конкретное изменение; сквозное доменное знание (термины, статусные модели, типы клиентов) живёт отдельно, в продуктовом контексте.

**Место baseline в потоке.** Снятие baseline — разовая подготовка по сервису (описываем «как есть» один раз), а не шаг фичи «с нуля». Внутри потока изменения легаси он запускается после decompose (§3.2), когда уже определены затронутые сервисы, у которых baseline ещё нет; на этапе intent сервис ещё не известен.

**Источники и их приоритет.** Baseline снимается из трёх источников с жёстким приоритетом; расхождения нужно разбирать:

| Источник | Роль | Приоритет |
| --- | --- | --- |
| Код | что система фактически делает — истина | высший |
| Тест-кейсы | вторичный сигнал; описывают, как тестировали, а не как работает | средний |
| Confluence\US | задокументированное намерение («зачем»), не доказательство поведения | низший |

Confluence структурирован и привязан к сервисам, поэтому агенту подаётся только пространство нужного сервиса, а не всё подряд. Ценность Confluence — не в снятии поведения, а в подсказке для бизнес-вопроса: он вскрывает **расхождения код↔Confluence** (поведение разошлось с намерением — сигнал для продукта). Флагами поднимаются все три вида расхождений: код↔тесты, код↔Confluence, Confluence↔тесты.

**Уровни уверенности.** Каждое снятое поведение агент помечает уверенностью, чтобы валидация инженера была содержательной, а не формальной:

| Уровень | Основание | Внимание инженера |
| --- | --- | --- |
| высокая | подтверждено и кодом, и тестом | беглое |
| средняя | выведено только из кода, теста нет | обязательное |
| низкая | источники противоречат друг другу | приоритетное |

**Цепочка:** reverse-spec агент (скилл «снять поведение», приоритет код > тесты > Confluence) → черновик baseline с пометками поведения, уверенности и расхождений → **инженер валидирует** технику и флаги, фокус на среднем/низком доверии → агент **переформулирует** каждое правило в бизнес-вопрос («система при X делает Y — это намеренное правило, баг или устаревшее?») → **продукт выносит вердикты**, глубина зависит от класса критичности сервиса → baseline принята (ложится в `openspec/specs/<сервис>/`, раскладка — Прил. G.4) → дальше обычный поток на изменение.

**Глубина продуктовой валидации — по классу критичности** (опираемся на существующую классификацию сервисов):

- критичные сервисы (биллинг, тарификация, тайна связи) — продукт проходит по каждому правилу вдумчиво;
- некритичные (внутренние сервисы) — выборочное подтверждение, без сплошного разбора.

**Роли и скиллы.** Reverse-spec ведёт один агент с двумя скиллами: снять поведение «как есть» и перевести его в бизнес-вопросы для продукта.

**Владение документацией.** По вердикту «документация устарела» агент готовит черновик обновления страницы Confluence через коннектор (сохраняя намерение, а не только поведение), владелец сервиса утверждает. Иначе reverse-spec будет находить одно и то же расхождение на каждом прогоне.

### 3.9 Утверждение и трассируемость

> *Калибруется в Фазе 0: механизм матрицы покрытия (связь код↔R-id, join по TC, политика гейта и привязка к классу критичности); проработка — отдельным проходом по трассируемости.*

Гейты — по §3.5 (человек, не агент). Итоговый артефакт трассируемости — матрица покрытия (требование × тест-кейс × код). Требование без `source` не принимается. Матрица сшивается через `R-id` ↔ TestIT-id (тест-кейсы живут в TestIT, требования — в репозитории), охватывая оба хранилища; изменение требования флагует связанные тест-кейсы TestIT.

- **Хранение:** матрица не ведётся руками — это **генерируемый в CI отчёт** (join `R-id` ↔ кейс TestIT ↔ автотест по номеру TC; код `R-id` не несёт). Источники версионируются (спеки — в git, кейсы — в TestIT); матрица прикладывается к MR и/или на дашборд, снапшот — на релиз для аудита.
- **Роль человека:** не строит, а **читает как сигнал** на гейте (есть ли дыры, приемлем ли радиус изменения) и решает по дыре (принять / завести тест); единственная ручная валидация — легаси-сопоставление `R-id` ↔ кейс TestIT.
- **Этап:** рождается на **Design** (`R-id` + `source`), наполняется на **Test**, служит **гейтом на Deploy** (элемент DoD).

### 3.10 Антипаттерны

- Спеку и пишет, и утверждает агент — галлюцинацию. Черновик — агент, утверждение — человек.
- Инженер подтверждает baseline целиком, без разбора; внимание должно идти на среднее и низкое доверие и на флаги.
- Продукту показывают техническое описание поведения вместо бизнес-вопроса — продукт не может дать вердикт и выпадает из процесса.
- Три источника слиты в гладкую спеку — спрятаны противоречия, ради которых reverse-spec затевался.
- Требования продублированы в Jira и в спеке — копии расходятся; требования живут только в спеке, тикет ссылается.

### 3.11 Межсервисные изменения

Фича часто трогает **много сервисов через публичный сервис продуктового слоя**. Пример: публичный метод `sip/v1/Create` на публичном сервисе (NGW/WEB) вызывает ~7 нижележащих сервисов (RI, NMS, Product Offering, CMA, Billing, Voice Cluster, Action History), каждый — своя команда. Единого «тех-лида на фичу» нет; модель остаётся SDD.

**Два слоя.** Продуктовый слой — публичный сервис (напр. NGW) + WEB: владеет публичным методом (клиентский API) и собирает поведение end-to-end. Нижележащие сервисы — каждый своя команда, свой внутренний контракт.

**Два уровня контракта (contract-first на обоих).**

- **Публичный контракт** (клиентский метод; REST-спека + proto) — внешне наблюдаемая поверхность. **К нему привязан Гейт 1 (бизнес)** — один на фичу (§3.6); владеют продукт + команда публичного сервиса.
- **Внутренние контракты** (публичный сервис → нижележащий сервис; proto/gRPC) — **к ним привязаны пер-сервисные Гейты 2 (техника)**, каждый у своей команды.
- Гейт 1 срабатывает на изменение **публичного** метода/поведения, независимо от того, какой слой его инициировал. Обратно совместимое изменение нижележащего сервиса, не меняющее публичный метод, → только его Гейт 2.
- Контракт (публичный или внутренний) не ломается в одностороннем порядке — только через версионирование и координацию через публичный сервис.

**Владение (тех-лида на фичу нет).**

- Каждый нижележащий сервис владеет своей частью: свой `changes/<id>/` (ссылается на контракт и фиче-R-id), свой Гейт 2, свои тесты, свой релиз.
- **Интегратор фичи — команда публичного сервиса** (NGW/WEB): владеет публичным методом, собирает и тестит связку **E2E**, делает клиентский релиз.
- Бизнес-готовность user story — на PO (Гейт 1).

**Релиз — два режима.**

- **По умолчанию — независимый.** Внутренний контракт обратно совместим → каждый нижележащий сервис деплоит сам после своего Гейта 2, своих тестов и проверки обратной совместимости контракта (proto breaking-change). **Выкладка кода в прод и включение фичи клиенту — разные события:** части (и даже новый публичный метод) можно выложить в прод заранее, но держать **выключенными для клиента** (feature-флаг или просто не публикуя метод). **Клиенту публичный метод становится доступен только после зелёного E2E-теста у публичного сервиса.**
- **Параллельный (синхронный).** Когда обратная совместимость невозможна или нет безопасного промежуточного состояния: части выезжают в одном согласованном окне вместе, с **согласованным откатом**; окно координирует команда публичного сервиса. По умолчанию стремимся к обратной совместимости, чтобы синхронный режим был редким.

**Покрытие — двухуровневое.**

- Пер-сервисная матрица (§3.9) — у каждой команды: R-id сервиса ↔ кейс TestIT ↔ автотест.
- Фиче-уровневое (E2E) покрытие — у команды публичного сервиса: публичный R-id фичи ↔ E2E-кейс ↔ E2E-автотест; проверяется перед публичным релизом.
- Склейка по фиче-R-id; единой «мегаматрицы» по всем внутренностям фичи нет.

**Рабочий пример: межсервисная фича от интента до клиента.**

*Фича:* в ответ `sip/v1/Create` добавить поле `sip_remaining` — сколько SIP ещё можно создать по тарифу. Трогает NGW (публичный сервис), Product Offering (лимит по тарифу), RI (текущее количество), WEB.

1. **Plan.** PO описывает интент через OpenCode-пресет; интент один на фичу, про публичный метод, ложится в репозиторий продукта (§3.12). PO утверждает.
2. **Design.** Агент разворачивает бизнес-спеку публичного метода (новое поле + критерии приёмки) → **Гейт 1 (продукт)**. **Разбор по слоям** — определить, какие сервисы и что предоставляют (Product Offering — лимит по тарифу, RI — текущее количество, NGW — сборку, WEB — показ) — **координирует команда публичного сервиса** (владеет публичным методом и знает весь сиквенс); но дизайн своей части пишет каждая команда сама. Каждая затронутая команда (Product Offering, RI, NGW, WEB) заводит свой `changes/<id>/` со ссылкой на фиче-R-id и внутренний контракт → **пер-сервисный Гейт 2**. Контракты согласуются contract-first (добавление поля — обратно совместимо).
3. **Build.** Каждая команда пишет свою часть в своём репозитории (параллельно/последовательно): Product Offering отдаёт лимит, RI отдаёт количество, NGW собирает и кладёт поле за флагом, WEB показывает.
4. **Test.** Каждый сервис — самопроверка + свои тесты + проверка обратной совместимости контракта. Публичный сервис — E2E всей связки `Create` с новым полем.
5. **Deploy.** Нижележащие — **Product Offering и RI** — катятся в прод независимо (обратно совместимо); **NGW** выкладывается со сборкой, но поле выключено для клиента (флаг). Когда все части в проде и **E2E зелёный — команда публичного сервиса (NGW) включает поле клиенту**.
6. **Покрытие.** Каждая команда — своя матрица; публичный сервис — фиче-E2E покрытие публичного R-id; склейка по фиче-R-id.

### 3.12 Раскладка в polyrepo (группа GitLab)

Продукт — **200+ микросервисов в группе GitLab, не монорепа**.

```text
группа GitLab: git.<...>/<группа>/
├── numbers-service/          ← сервис = репозиторий
│   ├── openspec/
│   │   ├── specs/            ← истина требований сервиса (+ baseline легаси, §3.8)
│   │   └── changes/<id>/     ← proposal / specs / design / tasks
│   ├── <код сервиса>
│   └── CONTEXT.md            ← подсказки агенту по локальности (§2.2)
├── billing-service/ …        (аналогично) × 100+
├── <репозиторий продукта>/   ← intent/ + openspec/changes/<id>/ (бизнес-спека, Гейт 1)
├── contracts/                ← общие proto: смешанная схема (см. ниже)
└── product-context/          ← доменный контекст + INDEX.md (§2.6)
```

- **`openspec/` — в каждом репозитории сервиса.** `specs/` (истина требований сервиса) + `changes/<id>/`. Владение, CODEOWNERS, гейты — пер-сервисные. Baseline легаси (reverse-spec, §3.8) ложится в `openspec/specs/` того же репозитория.
- **Общее — в отдельных репозиториях группы** (не дублируем в 200+ репо): **`product-context/`** (доменный контекст, §2.6; агент читает его поверх сервисного).
- **`contracts/` — временно смешанная схема** (часть сервисов на spine, часть в MTT-Apis, перенос постепенный). Детализация схемы и реестр контрактов — после выбора пути. *Калибруется в Фазе 0.*
- **Репозиторий продукта** — отдельный репозиторий группы: `intent/` и `openspec/changes/<id>/` с бизнес-спекой (`proposal` + `specs`); Гейт 1 мёржится сюда, `design` и `tasks` создаются в репозиториях сервисов шагом decompose (§3.2). Не путать с `product-context/`: это сквозное доменное знание с другим жизненным циклом и владельцем (§2.6). Имя репозитория не зафиксировано.
- **Неймспейс R-id: `<сервис>/R-<n>`** (`numbers/R-1`, `billing/R-1`). TestIT один на всю группу → R-id должен быть глобально уникален. Матрица покрытия (§3.9) по умолчанию **пер-сервисная**; при необходимости агрегируется по префиксу.
- **Межсервисная фича — по §3.11:** contract-first на двух уровнях (публичный контракт → Гейт 1; внутренние → пер-сервисные Гейты 2); тех-лида на фичу нет — интеграция и E2E на команде публичного сервиса; релиз в двух режимах (независимый по умолчанию / синхронный как исключение).
- **Единообразие обеспечивает платформа:** единый шаблон `openspec/`, маршрутизация приёмки по владельцам и защита веток — во всех репозиториях группы централизованно, а не руками в каждом. Механизм раскатки (шаблон для новых сервисов, скрипт MR для существующих, групповые настройки GitLab) и способ принудительного аппрува код-оунера — *калибруется в Фазе 0* (зависит в т.ч. от редакции GitLab).

## Часть 4. Стадии (plays)

### 4.0 Механика передачи между стадиями

Передача эстафеты между стадиями опирается на конкретный механизм поверх git и трекера, без нового тулинга.

**Три носителя сигнала.**

- **Git — истина и гейт.** Артефакт каждой стадии (`intent.md` → бизнес-спека → изменение сервиса → diff → MR) живёт в репозитории и передаётся следующей стадии как есть. Сигнал «пора утверждать» несёт **MR + CODEOWNERS**: запрос ревью автоматически маршрутизируется на нужного человека — это и есть уведомление о гейте. Merge = переход на следующую стадию.
- **Jira — отражение статуса.** Тикет показывает, на какой стадии изменение и на кого назначено, — для планирования и видимости; истиной не является (§3.4). **Механика синхронизации git → Jira в проработке:** не определены проект Jira, обязательные поля и валидаторы переходов, события-триггеры и то, кто создаёт тикет.
- **Orchestrator — маршрутизация внутри сессии.** Внутри одной стадии оркестратор вызывает нужную роль (`spec`, `coder`, `reviewer`) и подтягивает контекст по месту. Эстафету между стадиями и людьми он **не** несёт — это делают git и гейты.

**Два типа передачи — не путать.**

- **Внутри стадии (агентная, быстрая):** `intent` → черновик спеки делает `spec`; план реализации в `tasks` → код делает `coder`. Без человека на каждом шаге.
- **Между стадиями (человеческий гейт):** переход возможен только через утверждение человеком. Технически гейт = запрос ревью MR + защита веток; **кого спрашивают — решает CODEOWNERS по пути файла**: бизнес-спека (`proposal`/`specs`) → продукт (**гейт 1**), техдизайн (`design`/`tasks`) → инженер (**гейт 2**), код → владелец кода (merge).

**Обобщённый цикл — один и тот же на каждой стадии:**

```text
        ┌──────────────────────── повтор на каждой стадии ────────────────────────┐
        ▼                                                                          │
артефакт ──▶ MR ──▶ CODEOWNERS ──▶ ГЕЙТ ──▶ merge ──▶ следующая стадия ───────────┘
(в git)   (агент)   (маршрут       (человек
                    ревью          утверждает)
                    владельцу)
параллельно: git ──▶ Jira (отражение статуса и назначения; механика TBD)
```

**Как это выглядит на одном проходе (greenfield):**

1. Продукт утвердил `intent/example_intent.md`: MR смёржен в `master`. *(старт: человек; со зрелостью — CI-hook на merge)*
2. `spec`-агент разворачивает `intent` в `proposal`+`specs`, оформляет MR. CODEOWNERS шлёт запрос ревью **продукту** → **гейт 1** (продукт валидирует через OpenCode-пресет с человекочитаемой спекой, не через raw git, §7.1), merge.
3. После гейта 1 интегратор фичи запускает decompose (§3.2): агент открывает в репозиториях затронутых сервисов MR с заготовкой изменения сервиса (`proposal`); дальше в репозитории сервиса стандартным потоком (explore → propose) рождаются `specs` (дельта сервисной спеки), `design` и `tasks`. CODEOWNERS шлёт запрос ревью **инженеру** сервиса → **гейт 2**, merge = вход в Build.
4. Build → Test → Deploy идут тем же порядком: артефакт → MR → нужный человек по CODEOWNERS → гейт.

**Принцип синхронизации.** Истина — репозиторий (§3.4); Jira показывает, «где изменение и на ком», и при расхождении уступает репозиторию. Конкретная механика — TBD (см. выше).

**Ветвление.** Только `master` и короткие ветки через MR. Смёрженный MR в `master` = артефакт принят, гейт пройден. Состояние реализации определяет не ветка, а положение изменения в OpenSpec: `changes/<id>/` до реализации, архив после деплоя (§4.5).

**Автономия эстафеты (принцип 9).** На старте следующую стадию **запускает человек** (взял тикет, открыл сессию). По мере зрелости запуск черновика следующей стадии вешается на **CI-hook** (событие merge предыдущего артефакта), а человек остаётся только на гейтах. Триггер эволюционирует от ручного к событийному — гейты остаются человеческими.

### 4.1 PLAN

**Что меняется.** Раньше идея проходила через backlog, оценки и refinement, теряя авторский смысл на каждой передаче. Теперь автор идеи обсуждает её с агентом и фиксирует результат как `intent.md` в своих терминах.

**Артефакт:** `intent.md` — проблема, предлагаемый исход, затронутые пользователи и системы, ограничения, открытые вопросы (шаблон — TBD).

**Как исполнять.**

1. Автор описывает проблему агенту своими словами.
2. Агент задаёт вопросы аналитика: границы, пользователи, ограничения, критерий успеха.
3. Агент оформляет `intent.md` по шаблону (шаблон оформлен как skill).
4. Автор правит то, что агент понял неверно.
5. MR в общий версионируемый каталог `intent/` в репозитории продукта (§3.12).

**Gate и автономия.** Утверждает владелец по классу изменения (§3.6): бизнес-изменение → продукт-оунер (Гейт 1); чисто техническое (рефактор/техдолг) → инженер. Merge фиксирует решение. Автономии на старте нет — вход всегда человеческий.

**Антипаттерны.**

- Интент пишет не автор идеи, а посредник — при пересказе теряется исходный смысл.
- Шаблон заполнен формально, реальная проблема не описана — следующая стадия работает вслепую.

### 4.2 DESIGN — требования и дизайн (SDD)

Стадия целиком построена на SDD (фреймворк OpenSpec, нотация, разделение владения, потоки greenfield и legacy).

**Что меняется.** Раньше требования и дизайн — две фазы двух команд. Теперь агент разворачивает `intent` в спеку, а владение разделено: продукт отвечает за бизнес-требования, инженер — за техдизайн. Оба черновика пишет агент, ограниченный skills (безопасность, комплаенс, UX), и явно отмечает зоны риска. Один и тот же `spec`-агент работает в двух режимах: в репозитории продукта — только `proposal` + `specs`, в репозитории сервиса — полный цикл OpenSpec.

**Артефакт:** бизнес-спека — `proposal` + `specs` (бизнес, владелец — продукт, репозиторий продукта) и изменение сервиса — `proposal` + `specs` (дельта сервисной спеки) + `design` + `tasks` в репозитории каждого затронутого сервиса (техника, владелец — инженер); заготовку создаёт decompose (§3.2). Требования и сценарии — в формате OpenSpec (§3.3, шаблон — Прил. B).

**Как исполнять.**

1. Продукт с агентом разворачивает `intent` в бизнес-спеку; агент отмечает зоны риска и противоречия источников.
2. **Гейт 1 (бизнес-приёмка):** продукт принимает бизнес-требования.
3. **decompose:** интегратор фичи запускает агента; агент предлагает затронутые сервисы, интегратор подтверждает, агент открывает MR с заготовкой изменения сервиса (`proposal`) в репозитории каждого сервиса (§3.2).
4. Инженер с `spec`-агентом ведёт в репозитории сервиса полный цикл OpenSpec (explore → propose → apply): дельта сервисной спеки, `design`, `tasks` и реализация; каждый элемент ссылается на бизнес-требование (R-id); конфликты US ↔ proto ↔ требование — стоп-вопрос.
5. **Гейт 2 (техническая приёмка):** инженер принимает изменение сервиса целиком (`proposal`, `specs`, `design`, `tasks`). Это вход в Build.

**Gate и автономия.** Два человеческих гейта; утверждает человек, не агент. Автономии на старте нет; по мере зрелости черновик идёт без пошаговых подтверждений, но оба гейта остаются человеческими.

**Антипаттерны.**

- Спека переписывает контракт: proto остаётся истиной, спека описывает поведение и бизнес-правила. При конфликте — агент останавливается и задаёт вопрос.
- Требование без указания источника — через месяц никто не вспомнит, откуда оно и верно ли ещё.
- Техдизайн не ссылается на бизнес-требование — связь «что» и «как» потеряна.

### 4.3 BUILD — план и реализация

**Что меняется.** Раньше инженер читал дизайн и начинал писать код; «как именно» жило в голове, и первое, что видел ревьюер, — готовый diff. Теперь Build начинается с письменного плана реализации: агент в режиме планирования опирается на описанное поведение сервиса (baseline «как есть» для легаси / спеку требований для нового) и читает **релевантные части** кода, ничего не меняя, и **дополняет `tasks.md`** разделом «План реализации» (какие файлы, порядок, риски, чем доказываем); инженер правит его до написания кода.

**Артефакт:** `tasks.md`, дополненный разделом **«План реализации»** (Приложение C) → diff + тесты. Отдельного `plan.md` нет: план реализации — это код-обоснованное расширение утверждённой на Гейте 2 нарезки, а не второй документ.

**Как исполнять.**

1. Сессия в режиме планирования; на входе — утверждённое изменение (`design`+`tasks`, Гейт 2) поверх описанного поведения сервиса: для легаси — baseline «как есть» (`openspec/specs/<сервис>/`, §3.8), для нового — спека требований.
2. Запросить план реализации: какие файлы меняются, в каком порядке, какие тесты это докажут — агент дописывает это в `tasks.md`.
3. Разобрать план: что может сломаться, какой шаг рискованнее всего, какие альтернативы отвергнуты и почему.
4. Итерировать, пока по плану смог бы реализовать другой инженер.
5. Коммит обновлённого `tasks.md`, затем реализация (при хорошем плане часто в один проход). Отклонение от плана фиксируется правкой `tasks.md` в том же коммите; для этого может повести hook.

```text
BUILD: [А] агент [Ч] человек
    ══ plan mode (агент читает спеку + релевантный код, НЕ пишет)
design+tasks (Гейт 2 пройден)
        │
        ▼
══════ PLAN MODE ══════════════════════════════
[А] читает спеку сервиса + релевантный код,
    дополняет tasks.md разделом «План реализации»
    (файлы, порядок, риски, чем доказываем)
        │
        ▼
┌─────────────────────────────────────────────┐
│ ЧЕКПОИНТ ПЛАНА [Ч] — НЕ гейт (нет merge)    │
│ «агент понял? радиус приемлем?»             │
│ не ок ─▶ правит план (кода ещё нет) ─┐      │
│ ◀────────────────────────────────────┘      │
│ ок ─────────────────────────────────┐       │
└────────────────────────────────────────┼─────┘
                                         ▼
[А] пишет код+тесты по плану ─▶ diff → TEST
Зрелость: для рутины [Ч]-чекпоинт отключается (автономия по метрикам).
```

**Gate и автономия.** Утверждение плана реализации — **внутри-Build чекпоинт, не третий гейт**: инженер утверждает дополненный `tasks.md` до генерации кода (Гейт 2 на `design`+`tasks` уже пройден на Design). По мере созревания контроля (контекст репозитория, skills, hooks, тест-набор) для рутинных задач включается автоматический режим: инженер утверждает план, агент применяет правки без подтверждения каждого шага, а внимание человека смещается на проверку итогового артефакта.

**Антипаттерны.**

- Код пишется без утверждённого плана — ревьюер впервые видит замысел уже в готовом diff.
- Знания зашиты в промпты агентов — файлы ролей должны содержать только роль и маршрутизацию, а не доменные факты.
- Контекст репозитория раздут — релевантное теряется среди устаревшего, растёт расход токенов без пользы.

### 4.4 TEST — самопроверка и непрерывные evals

**Что меняется.** Раньше сигнал приходил от CI, тестировщика, прод зоны. Теперь каждая сессия проверяет свою работу до человека, а конфигурация/поведение агента регрессионно тестируется, как код (evals).

**Артефакт:** тесты + результаты evals (пройденные проверки приложены к MR).

**Как исполнять — контур самопроверки.**

1. Свернуть проверку в одну команду (`make test`), возвращающую ненулевой код при провале; пример корректного вывода описать в контексте репозитория.
2. Дать агенту измеримую цель: «все тесты в X зелёные», «скриншот совпадает с макетом», «эндпоинт возвращает 200 с новым полем».
3. **В задаче на изменение поведения** агент обновляет и добавляет тесты в том же MR; недостающее обновление ловит проверка «изменённое поведение требует изменённых или добавленных тестов». Независимый приёмочный слой (ниже) агенту недоступен.
4. **В задаче на багфикс** — сначала падающий тест: агент воспроизводит баг тестом, коммитит его, затем чинит код; hook запрещает правку существующих тест-файлов только в задаче на исправление. Тест, существовавший до фикса и неизменяемый агентом, доказывает, что баг ушёл. Подробный процесс работы с багами описывается отдельно.
5. Верификация — часть определения «готово»: прогнать тесты и показать вывод до отчёта о завершении.
6. Тесты агента проверяются на то, что они ловят ошибки: поломка строки кода или мутационный прогон должны ронять тесты; доля пойманных внесённых ошибок (mutation score) — сигнал качества тестов. Покрытие само по себе — слабый сигнал: агент пишет и код, и тесты к нему.

**Как исполнять — непрерывные evals (аналог стадийного QA-гейта).**

1. Собрать 20–50 реальных задач с принятым исходом.
2. Оформить каждую как eval: промпт плюс проверки (тесты зелёные, линтер чист, поведение не изменилось, политика соблюдена). Проверки детерминированные; модель-судья (LLM-as-judge) — только там, где детерминированной проверки нет, и не в Фазе 0.
3. Набор гоняется в CI по cron, а любое изменение конфигурации агента (контекст репозитория, skills, hooks) — она управляет агентом и требует постоянных проверок, как код.
4. Изменение конфигурации, опускающее pass-rate ниже порога, ревьюится до merge. Порог хранится файлом в репозитории конфигурации агента и меняется через MR; владелец — Eval / Quality owner.

**Независимый приёмочный слой — не всё отдаём LLM.** Критический смоук/приёмочный слой пишет и поддерживает человек (AQA), выводя его из Given/When/Then; этот слой недоступен агенту-кодеру (hook) и служит независимым уровнем проверки. LLM-сгенерированные проверки добавляют охват поверх, но не заменяют человеческую проверку.

**Gate и автономия.** Верификацию-перед-готовностью и запрет правки тестов в задаче на исправление реализуем как hooks там, где нужна гарантия. Доказательство — вывод `make test` или скриншот-сравнение, приложенные к MR. Утверждает владелец кода в MR.

**Антипаттерны.**

- Агент, который чинит код, может ослабить проверку этого кода, переписав тест.
- Evals собрали один раз и забыли — набор нужно поддерживать: устаревшие кейсы убирают, новые добавляют по результатам наблюдений.

### 4.5 DEPLOY — двунаправленное ревью и gate

> *Калибруется в Фазе 0: пороги автономии по окружениям (dev/staging/prod).*

**Что меняется.** MR ждал ревьюера, качество плавало с нагрузкой. Теперь все MR получают одинаковый набор проверок (агент ревьюит входящие MR и отрабатывает комментарии на своих), а человек поднимается на уровень «делает ли изменение то, что задумано, и приемлем ли риск».

**Артефакт:** до merge — находки ревью (в треде MR); после подтверждённого деплоя — запись релиза и архивация изменения (ниже).

**Как исполнять.**

1. Тех-лид пишет политику ревью `REVIEW.md`: проходы (баги и логика; безопасность и уязвимости; соответствие `spec.md`, `tasks.md` и дизайн-принципам), что считается важным, а что — мелочью, что пропускать (шаблон TBD).
2. **Агент советует — мержит человек.** Комментарии агента — рекомендации: сами по себе не утверждают и не блокируют MR. Влить код можно только с апрувом живого владельца кода — держит защита веток.
3. **Замечания разбирает разработчик.** Разработчик стягивает MR локально и правит замечания вместе со своим агентом, в том же интерфейсе, где писался код. Агент по комментарию в GitLab автономно не правит: ветка может устареть, работа идёт параллельно, а человек знает больше контекста, чем агент. Замечания и ответы остаются в треде MR.

Повторяющиеся замечания и ежемесячная калибровка ревью отложены на следующие фазы.

**Запись релиза и архивация.** После подтверждённого деплоя в прод:

1. **Запись релиза** — GitLab Release или тег со ссылками на MR и R-id.
2. **Архивация изменения** — `changes/<id>/` уходит в архив OpenSpec, дельта сливается в `openspec/specs/<сервис>`, так сервисная спека остаётся равной фактическому поведению.

Для межсервисной фичи каждый сервис архивирует своё после своего деплоя; бизнес-спеку в репозитории продукта архивирует интегратор, когда E2E зелёный и фича включена клиенту (§3.11).

**Ревью и защита веток.**

- *Ревью-процесс* у нас есть: минимум один аппрув. В AI-native он становится двунаправленным — агент и даёт, и получает ревью, человек фокусируется на замысле и риске.
- *Ревьюер сильнее исполнителя.* Код, сгенерированный более дешёвой/быстрой моделью, ревьюит модель более сильного класса — она ловит другие классы ошибок, чем автор. Разрыв в силе модели между генерацией и ревью — часть контроля качества, а не только человеческий аппрув.
- *Защита веток* — настройки GitLab, не дающие смержить в защищённую ветку без выполнения условий. Это техническое строгое правило «агент действует до gate, но не за него».
- **Принятый стандарт (GitLab):** ветка `master` защищена; прямой push запрещён; обязателен минимум один аппрув владельца кода-человека (через CODEOWNERS); обязателен зелёный pipeline; всё, что пишет агент, приходит только как MR — прямого пути в `master` у агента нет; агент действует под собственной идентичностью, чтобы в логах pipeline его действия отделялись от действий инженера.

**Gate и автономия.** Разделение полномочий: агент, написавший код, не имеет способа его утвердить. Gate релиза — hook типа «спросить»: прод-деплой блокируется, пока назначенный владелец не авторизует (авторизация релиза — на владельце кода / тимлиде). В prod агент готовит релиз, а авторизует человек, и hook это проверяет. Автономия в dev и staging — целевая модель: она реализуется настройкой пайплайна и защищённых окружений владельцем пайплайна и калибруется по метрикам зрелости (принцип 9); отложена на следующие фазы.

**Антипаттерны.**

- Находки агента автоматически мержат или блокируют MR — человек убран из петли, ответственность размывается.
- У агента есть прямой путь в `master` — теряется разделение полномочий.
- Поток мелких замечаний топит важные — ревью перестают читать.

### 4.6 Критерии завершения: DoD и критерии приёмки

Критерий приёмки и Definition of Done (DoD) — разные вещи: первый относится к одному требованию, второй — к стадии, фиче или релизу. Различаются четыре уровня:

| Уровень | Что определяет |
| --- | --- |
| Критерии приёмки | когда выполнено конкретное требование: Given/When/Then к каждому требованию (§3.3) |
| DoD стадии или агента | когда стадия или роль агента считается завершённой и работа выходит на гейт (условие входа в гейт) |
| DoD фичи | когда фича считается сделанной, включая трассируемость (§3.9) и E2E для межсервисной фичи (§3.11) |
| DoD релиза | когда релиз можно авторизовать (hook «спросить», §4.5) |

Содержание уровней и ответственные здесь не фиксируются: их определяет отдельная проработка.

## Часть 5. Governance, безопасность, ответственность

Governance ведётся набором артефактов (политика, манифест, инженерные политики, enablement-плейбуки) и технических контролей. Ниже — их карта и статусы: часть уже действует, часть создаётся.

### 5.1 Политика использования AI

Каждый документ версионируется, у каждого — назначенный владелец.

- **Правила по данным — что можно и нельзя отправлять в модель.** Действует **Манифест** (`enablement/manifest.md`), обязателен к прочтению всеми. Целевая орг-политика (централизованная, через шлюз, §2.5) — создаётся; до неё правила держит Манифест.
- **Реестр обязательных правил, оформленных как skills и hooks** (в работе) — единый список того, что применяется одинаково во всех командах (секреты не логировать, внешний API проходит проверку безопасности, merge в `master` только с аппрувом); у каждого правила — ответственный владелец.
- **Правила атрибуции:** каждое действие агента привязано к человеку, который его запустил.
- **Референс инженерных политик** (оформляются как skills/hooks, §2.2) — источник, из которого платформа централизованно доставляет конвенции агентам; не изобретаем с нуля: обработка ошибок; стандарты тестирования; дизайн API; здоровье кода; бюджеты производительности; безопасность; дизайн-принципы фронта; структура модулей; формат задач и TDD. Каждая политика — документ с владельцем, **подпёртый контролем** (линтер / CI / hook / ревью-промпт), а не просто текст. Содержание политик — зона со-авторства команд (подробно — Часть 7).
- **Централизованная остановка/отзыв (kill-switch).** Платформа владеет ключами и доступом → может немедленно отозвать доступ агента, заглушить его в CI и остановить массовые действия. Триггеры (аномальный объём изменений, всплеск отклонений на ревью/evals, инцидент безопасности) — часть политики.

### 5.2 Аудируемость

Артефакт-цепочка служит аудиторским следом: кто просил, что сделал агент, кто утвердил — в git-истории. Дополнительно: сессии агентов логируются (телеметрия в наш стек — Prometheus / Grafana / Keep), решения hooks пишутся с временной меткой и вердиктом (пропустить / спросить / заблокировать).

### 5.3 Ответственность и переход ролей

Ответственность ролей и их переход опираются на **ролевые плейбуки** и **Foundations** (манифест безопасности + базовая грамотность): там зафиксировано, кто за что отвечает и как к этому готовят.

## Часть 6. Измерение

Под AI-SDLC заводим отдельную телеметрию. Baseline снимаем до старта, дальше сравниваем по фазам.

**Два слоя метрик.**

- **Метрики потока:** **время «идея → прод»** · **стоимость на поставленную фичу/изменение** · **доля дефектов в проде**.
- **Операционные метрики:** DORA и AI-специфичные метрики.

**Операционные метрики:**

| Группа | Метрика | Источник | Тип |
| --- | --- | --- | --- |
| **DORA** | Lead time for changes | GitLab / Argo | результат |
|  | Deployment frequency | Argo CD | результат |
|  | Change failure rate — на старте прокси **rollback/hotfix-rate** | деплой-история (Argo); incident-лог → CFR позже | страховочная |
|  | MTTR | трекер инцидентов | страховочная |
| **AI-специфичные** | Доля изменений, влитых с первого прохода | метаданные MR | скорость |
|  | Pass-rate evals (конфигурация агента) | набор evals в CI | качество |
|  | Время до первого ревью | метаданные MR | поток |
|  | Время ревью на MR | метаданные MR | поток |
|  | Доля автономных действий за gate без касания человеком | логи телеметрии | зрелость |
|  | Циклы доработки на изменение | история MR | качество |
| **Страховочные** | Доля дефектов в проде / escape rate (**baseline есть**) + абсолют | существующий учёт дефектов | качество (основной противовес) |
|  | Находки безопасности (до merge против прода) | ревью / сканы | безопасность |
|  | Стоимость обращений к модели на смерженное изменение | биллинг бэкендов | стоимость |

**Baseline и цели.** DORA сегодня не измеряется: до старта реально снимаются **lead time и deployment frequency** (метрики скорости) и текущее время ревью. **Доля дефектов в проде (defect escape rate): по ней baseline существует давно.** **Change-failure** на старте можно замерять через **прокси — rollback/hotfix-rate** (из деплой-истории).

**Статус метрик.** Формулы и события начала и конца метрик (например, «идея → прод») определяются на следующих фазах; до этого значения — ориентиры, а не KPI.

**Метрики скорости нужно читать в паре с качеством.** Рост скорости сам по себе ни о чём не говорит, если падает качество. Поэтому: долю влитого с первого прохода смотрим вместе с числом доработок. Частоту деплоев — вместе с **долей дефектов в проде и rollback-rate**. Ни одна метрика скорости не оценивается отдельно от парной метрики качества.

**Долю дефектов смотрим вместе с абсолютом.** Агент генерирует больше кода быстрее, поэтому абсолютное число дефектов может вырасти, даже если *доля* пойманного до merge улучшилась.

## Часть 7. Управление изменениями и переход людей

Управление изменениями ведётся отдельным потоком, параллельным технической проработке.

### 7.1 Enablement по ролям

Переход каждой роли раскрыт в **ролевых плейбуках** (разработчик, продукт/PM, аналитик, QA) и в **Foundations** (старт с нуля: что такое LLM/агент, базовая грамотность, манифест безопасности). Методика на них ссылается, не дублирует. Ключевые опоры перехода:

- **Продукт** учится не писать спеки, а проверять и утверждать их; работает через «продуктовый режим» OpenCode (без git и терминала).
- **Инженеры (DEV + QA)** — от написания кода к авторству спек/планов, верификации и skills/hooks; критический приёмочный слой пишет и держит человек (AQA), недоступно агенту.
- **Фаза погружения** на личных учётках (квартал, параллельно Фазе 0) под манифестом безопасности; успех — по способности и безопасности, не по пропускной способности.

### 7.2 Процесс

Процессные ритуалы и перестройка производственного процесса (ритм планирования — PI Planning, PBV/ABV; Definition of Done; иерархия работ в Jira; авторизация прод-релиза; роль Agile Lead) **прорабатываются в Фазе 0**.

### Приложение B. Шаблон `spec.md` (формат OpenSpec)

Дельта-спека изменения лежит в `openspec/changes/<id>/specs/<capability>/spec.md`; после архивации требования переносятся в `openspec/specs/<capability>/spec.md`. Противоречия источников и открытые вопросы, которые блокируют утверждение, записываются в `proposal` (раздел Open questions), а не в спеку.

```markdown
## ADDED Requirements
### Requirement: {краткое название поведения}
Система SHALL {поведение одним предложением}.
id: R-1
source: intent, DoD п.2
#### Scenario: {основной случай}
- **GIVEN** {предусловие}
- **WHEN** {действие}
- **THEN** {результат}
#### Scenario: {ошибка или краевой случай}
- **GIVEN** {предусловие}
- **WHEN** {действие}
- **THEN** {отказ + код}
## MODIFIED Requirements
### Requirement: {название существующего требования без изменений}
{полный новый текст требования; первая строка — с SHALL или MUST}
id: R-2
source: {источник}
#### Scenario: {название}
- **GIVEN** {предусловие}
- **WHEN** {действие}
- **THEN** {результат}
## REMOVED Requirements
### Requirement: {название удаляемого требования}
**Reason**: {почему удаляется}
**Migration**: {что использовать вместо}
```

Правила, которые проверяет CI (§3.3):

- первая строка под `### Requirement:` содержит `SHALL` или `MUST`; `id:` и `source:` — после неё;
- у каждого требования — `id: R-<n>`, `source:` и минимум один `#### Scenario:` (ровно четыре `#`);
- шаги сценария — строки `- **GIVEN**`, `- **WHEN**`, `- **THEN**`;
- `openspec validate --strict` проходит.

## Ограничение на мелочи

### Приложение F. Глоссарий

- **Артефакт-цепочка** — последовательность версионируемых файлов (intent → spec → tasks → diff → MR), одновременно передача между стадиями и аудиторский след.
- **Продукт (продуктологи)** — группа продуктовых сотрудников (PO, PM, бизнес-аналитики, ~20 человек), владелец бизнес-требований (`proposal` + `specs`) и Гейта 1 (бизнес-приёмка). Не путать с «сервисом/продуктом» как ПО и с «продуктовым контекстом» (§2.6).
- **Бизнес-спека** — бизнес-требования к фиче на уровне продукта (`proposal` + `specs`); владелец продукт, утверждается на Гейте 1. Не путать с сервисной спекой.
- **Сервисная спека** — текущее поведение и контракты одного сервиса, лежит в `openspec/specs/<сервис>` его репозитория; для легаси начинается с baseline.
- **Изменение сервиса** — папка `changes/<id>/` в репозитории сервиса из четырёх артефактов (`proposal`, `specs` как дельта сервисной спеки, `design`, `tasks`); принимается на Гейте 2.
- **Публичный сервис** — сервис публичного слоя (например NGW), владеющий публичным методом и собирающий фичу из нижележащих сервисов; его команда — интегратор фичи.
- **Оркестратор** — только роль агента (L3): маршрутизирует задачу между ролями внутри сессии. Сервис публичного слоя оркестратором не называется.
- **Шлюз** — внутренний LLM-прокси на границе L2↔L1 (§2.2); слово без уточнения означает только его.
- **Критерии приёмки** — условия, при которых выполнено конкретное требование: Given/When/Then к каждому требованию (§3.3). Не путать с DoD.
- **Definition of Done (DoD)** — критерии завершения стадии или агента, фичи, релиза; четыре уровня вместе с критериями приёмки описаны в §4.6.
- **Требование и сценарий (OpenSpec)** — блок `### Requirement:` с нормативной фразой (`SHALL`/`MUST`) и минимум одним блоком `#### Scenario:` в шагах GIVEN/WHEN/THEN; формат проверяет `openspec validate --strict` (§3.3, Прил. B).
- **Evals (оценочный набор)** — набор реальных задач с принятым исходом, оформленных как проверки (тесты зелёные, линтер чист, поведение не изменилось, политика соблюдена). Гоняется в CI по cron и на любое изменение конфигурации агента (контекст, skills, hooks) — регрессия на самого агента, как тесты на код. Изменение, опускающее pass-rate ниже порога, ревьюится до merge (§4.4).
- **Hook** — детерминированная проверка на действие агента: пропустить / спросить / заблокировать.
- **Продуктовый (доменный) контекст** — сквозное доменное знание (термины, статусные модели, типы клиентов, интеграции), не привязанное к одному сервису; отдельно от baseline легаси (§2.6, §3.8).
- **Skill** — версионируемое обязательное правило или процедура организации, применяется агентом по описанию.
- **Контур самопроверки** — способ агента проверить свою работу до человека (тесты, сборка, скриншот).
- **Gate** — точка, где продолжение требует утверждения человеком.
- **Защита веток** — настройки, не дающие смержить в защищённую ветку без выполнения условий (аппрув, зелёный pipeline, запрет прямого push).
- **CODEOWNERS** — файл-механизм в репозитории (GitLab/GitHub), сопоставляющий **пути файлов → их владельцам** (людям/командам). MR, затронувший эти пути, автоматически запрашивает ревью у владельцев; с защитой веток их аппрув обязателен для merge. Это **не роль доступа GitLab** (Owner / Maintainer / Developer), а маршрутизация ревью по пути файла — так гейты попадают к ответственным (§3.5, §4.5).
- **Доля автономных действий** — доля действий агента, прошедших за gate без ручного касания.
- **Обращение к модели (inference)** — один запрос к LLM и её ответ (вход → выход). Тарифицируется по объёму текста (токенам). Модель при этом не обучается, а только используется. На одну задачу агент делает много обращений подряд, поэтому стоимость одной задачи складывается из десятков-сотен таких вызовов.
- **Токен** — минимальный кусочек текста, которым модель считает вход и выход; по числу токенов провайдер выставляет счёт.

### Приложение G. Примеры контекстных файлов

**G.1 `product-context/INDEX.md`** (индексируется по релевантности):

```markdown
# Product-context INDEX
Агент читает в начале ТОЛЬКО этот индекс, выбирает 1–3 релевантных файла и грузит их (принцип 4).
| Файл | Что внутри (одной строкой) | Читать, когда задача про… |
|---|---|---|
| glossary.md | Термины домена (номер, ресурс номера, AMD, speech analytics) | незнакомые термины |
| client-types.md | Типы клиентов + матрица прав/ограничений | права, доступ, ограничения по типу |
| number-lifecycle.md | Статусная модель номера (Active/Blocked/…) и переходы | статусы, смена состояний |
| number-attributes.md | Атрибуты номера (call_record, speech_analytics, amd…): смысл, кто включает | поля GetAttributes, флаги функций |
| billing-rules.md | Правила тарификации | биллинг, стоимость, тарифы |
| voice-rules.md | Голосовые вызовы и запись разговоров | звонки, запись, транскрибация |
Факт без источника в файлы не попадает; каждый доменный файл — с frontmatter (name/description/updated/owner).
```

**G.2 Корневой `CONTEXT.md` репозитория сервиса** (всегда загружается, ≤1 стр.):

```markdown
# Repo context
## Сборка и тесты
- Сборка: `make build` · Тесты: `make test` (ненулевой код при провале) · Линт: `make lint`
## Конвенции
- JSON: snake_case; URL: kebab-case; ошибки — RFC 7807
- proto — истина контракта; спека — поведение
## Архитектура (кратко)
- gRPC-сервис; API — `api/`, логика — `internal/`; общие контракты (proto) — в репо `contracts/`
## Грабли
- Не звать чужие сервисы напрямую — через клиент, сгенерированный из `contracts/`
## Где искать больше (грузить по месту, не дублировать сюда)
- Локальный контекст модуля — `internal/<module>/CONTEXT.md` · ADR — `docs/adr/` · раннбуки — `docs/runbooks/`
- Общие контракты — репо `contracts/` · доменные факты — репо `product-context/INDEX.md`
```

**G.3 Локальный `CONTEXT.md` модуля** (напр. `billing-service/internal/charging/CONTEXT.md`, индексируется по локальности):

```markdown
# Context: charging module
## Особенности
- Идемпотентность списаний по `idempotency_key`; суммы — в минимальных единицах (копейки)
## Тесты
- `make test-charging`; фикстуры — только синтетика
## Грабли
- Не менять `contracts/billing.proto` без версии — контракт публичный
```

**G.4 Где что лежит — раскладка в polyrepo.** Требования, код и контекст — **три разные вещи с разной ролью** (подробнее — §3.12). Раскладка — polyrepo: сервис = отдельный репозиторий группы GitLab, `openspec/` в каждом.

```text
git.<...>/<группа>/                        ← группа GitLab, сервис = отдельный репозиторий
│
├── billing-service/                       ← репозиторий сервиса
│   ├── openspec/
│   │   ├── specs/                         ← ИСТИНА ТРЕБОВАНИЙ сервиса («что делает»)
│   │   │   └── spec.md                    ← as-is baseline легаси (§3.8): поведения
│   │   │                                     (требования + сценарии) + уверенность + вердикты продукта
│   │   └── changes/
│   │       └── 2026-add-call-record/      ← изменение «в полёте»
│   │           ├── proposal.md            бизнес (продукт, гейт 1)
│   │           ├── specs/                 дельта требований
│   │           ├── design.md              техника (инженер, гейт 2)
│   │           └── tasks.md               нарезка + «План реализации» (§4.3)
│   │                                      (принятое → мержится в specs/ → архив, §3.2)
│   ├── api/  internal/                    ← КОД сервиса
│   └── CONTEXT.md                         ← подсказки агенту по локальности (G.3), НЕ требования
│
├── numbers-service/ …                     ← аналогично, свой openspec/ × 100+
│
├── contracts/                             ← общие proto: смешанная схема (§3.12)
└── product-context/                       ← сквозное доменное знание + INDEX.md (G.1)
TestIT (вне git) ─── кейсы с тегом R-id (<сервис>/R-n); связь с кодом по номеру TC (§3.9)
```

- **Спека ≠ код ≠ контекст.** Спека (требования) — в `openspec/specs/` репозитория сервиса; код — там же; контракт — proto (общие proto: смешанная схема, §3.12); контекст (`CONTEXT.md`, `product-context/`) — подсказки агенту, не истина. As-is baseline легаси — это **спека**, лежит в `openspec/specs/` своего сервиса.
- **Polyrepo:** `openspec/` — в каждом репозитории сервиса; `product-context/` — отдельным репозиторием группы, общие proto — смешанная схема (§3.12). R-id неймспейсится префиксом сервиса (`<сервис>/R-n`), т.к. TestIT один на группу. Подробнее — §3.12.
