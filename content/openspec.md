## 1. SDD: что это и зачем

**Коротко (из источника):** spec отвечает на вопрос «что», код — на вопрос «как». Change — единица работы, в которой изменение живёт до архивации.

Возьмём задачу «добавить двухфакторную аутентификацию в ЛКР Exolve». В названии нет главного: сколько живёт код, как часто его можно отправить повторно, что делать при потере телефона. SDD фиксирует эти решения в спецификации до кода: что система должна делать, в каком поведении это выражается и как проверить результат.

**Спецификация становится источником истины для человека и агента.** Код приводит систему в соответствие с ней, а не наоборот.

### 1.1 Что это даёт на практике

- **Агент не додумывает поведение.** Он читает его из spec: срок действия кода, правила повторной отправки, реакцию на просроченный ввод. Если ответа в spec нет, это видно до реализации, а не после.
- **Ревью идёт на уровне замысла.** Требования и сценарии обсуждают до кода, поэтому неверное решение видно раньше.
- **Понятно, что считать готовым.** У требования есть проверяемый сценарий, поэтому приёмка опирается на описанное поведение, а не на ощущение, что «вроде работает».
- **Решения и причины остаются в репозитории.** Через месяц можно открыть change и увидеть, почему выбрали десять минут, а не пять, и какие ограничения обсуждали.

Поэтому **ревью change начинается не с диффа, а с вопроса: какое поведение меняется и чем это подтверждается.**

### 1.2 Чем отличается от «спеки в вики»

Отдельного сравнения со «спекой в вики» в документации нет. Отличия следуют из перечисленных свойств OpenSpec:

- spec лежит в git **рядом с кодом** — каталог `openspec/specs/`, коммитится вместе с кодом, а не живёт отдельным документом;
- изменение оформляется **change-папкой** с ревью замысла до кода и слиянием дельты в spec после архивации, то есть у спеки есть цикл жизни, а не одна версия «на все времена»;
- требование имеет **проверяемый сценарий**, поэтому из спеки выводятся приёмка и автотесты;
- spec — **контекст для агента**: чего в ней нет, агент додумает, и это видно до реализации;
- решения и причины изменения остаются в **истории репозитория**, а не в переписке.

### 1.3 Глоссарий

| Термин | Значение |
| --- | --- |
| **spec** | Описание текущего поведения системы. Лежит в `openspec/specs/`. |
| **change** | Одна единица работы: proposal, delta, design, tasks. Лежит в `openspec/changes/`. |
| **delta** | Часть change, которая описывает добавленные, изменённые или удалённые требования. |
| **archive** | Каталог завершённых changes. При архивации delta вливается в spec. |
| **store** | Отдельный git-репозиторий для планирования, зарегистрированный на машине. |
| **reference** | Ссылка из `config.yaml` кодового репозитория на store для read-only контекста. |

## 2. Установка и инициализация

Страница доводит пустой проект до работающих команд `/opsx-*` в **Claude Code, OpenCode и Cursor**. После неё понятно, какие файлы появились, что в них лежит и как обновлять набор команд.

### 2.1 Требования

Нужна актуальная **LTS-версия Node.js**. Проверка:

```bash
node --version
```

Если команда отвечает версией — Node.js установлен. Если нет — установить актуальную LTS-версию.

### 2.2 Установка

Пакет ставится глобально через npm:

```bash
npm install -g @fission-ai/openspec@latest
openspec --version
```

- Первая команда скачивает пакет и кладёт бинарник в глобальный каталог npm.
- Вторая проверяет, что оболочка находит `openspec`, и печатает версию.
- Пустой ответ или `command not found` означают, что каталог глобальных бинарников не в PATH — его нужно добавить в PATH.

Для macOS и Linux есть установка через Homebrew: `brew install openspec`. **Основной путь — npm**: он одинаков на всех платформах. Выбрать **один способ на машину**: две установки сразу дают два бинарника в PATH, и тогда непонятно, какая версия отвечает на `openspec --version`.

### 2.3 Инициализация

Перейти в корень проекта — туда, где лежит `.git`:

```bash
openspec init
```

Команда спросит, для каких инструментов настроить проект, и предложит список: отметить нужные стрелками и подтвердить.

Для Claude Code, OpenCode и Cursor набор задаётся флагами, без диалога:

```bash
openspec init --tools claude,opencode,cursor
```

Такой вызов подходит для скриптов, CI и повторной инициализации: команда не ждёт ввода.

Флаг `--no-animation` убирает анимацию приветствия — для скриншотов и логов CI, где лишние кадры мешают читать вывод:

```bash
openspec init --tools claude,opencode,cursor --no-animation
```

После инициализации трёх инструментов: по **шесть команд и скиллов** на каждый, конфиг — в `openspec/config.yaml`.

### 2.4 Что появилось в проекте

```text
project/
├── openspec/
│   ├── specs/                 # спеки: текущее поведение системы
│   ├── changes/               # активные change
│   │   └── archive/           # завершённые change
│   └── config.yaml            # context, rules, схема; правится руками
├── .claude/                   # команды и скиллы (генерируются)
├── .opencode/                 # команды и скиллы (генерируются)
└── .cursor/                   # команды и скиллы (генерируются)
```

Кто за что отвечает:

| Каталог | Что внутри | Зачем |
| --- | --- | --- |
| `openspec/` | `specs/`, `changes/`, `changes/archive/` | Спеки и change. **Коммитятся вместе с кодом.** |
| `openspec/config.yaml` | `context`, `rules`, схема | Настройки агента. Правится руками. |
| `.claude/`, `.opencode/`, `.cursor/` | Команды и скиллы | **Генерируются.** `openspec update` перезапишет их. |

Правило: текст команды менять в **шаблоне или конфиге**, а не в файле `.claude/`, `.opencode/` или `.cursor/` — при следующем `openspec update` правка пропадёт.

Про файл правил проекта: на просмотренных страницах OpenSpec он отдельно не описан (`AGENTS.md`/`CLAUDE.md` — термины Foundations); настройки агента в OpenSpec живут в `openspec/config.yaml` (`context`, `rules`, схема). Общее понятие файла правил проекта разобрано в [Foundations](foundations.md).

### 2.5 Разница в вызове

| Claude Code | OpenCode | Cursor |
| --- | --- | --- |
| `/opsx:propose` | `/opsx-propose` | `/opsx-propose` |
| `/opsx:apply` | `/opsx-apply` | `/opsx-apply` |
| `/opsx:archive` | `/opsx-archive` | `/opsx-archive` |
| `/opsx:explore` | `/opsx-explore` | `/opsx-explore` |
| `/opsx:sync` | `/opsx-sync` | `/opsx-sync` |
| `/opsx:update` | `/opsx-update` | `/opsx-update` |

В Claude Code — двоеточие, в OpenCode и Cursor — дефис. Это **команды в поле ввода агента**, а не в системной оболочке. Shell про `/opsx:propose` ничего не знает и вернёт ошибку.

### 2.6 Обновление

Порядок имеет значение. Сначала обновить пакет:

```bash
npm install -g @fission-ai/openspec@latest
```

Если ставили через Homebrew — `brew upgrade openspec`.

Затем выполнить **в проекте**:

```bash
openspec update
```

`openspec update` перезаписывает сгенерированные команды и скиллы по текущим шаблонам пакета. Если запустить `update` на старом CLI, новых workflow в проекте не появится: шаблоны останутся прежними. Отсюда правило: **сначала пакет, потом `update`**.

После установки открыть Claude Code, OpenCode или Cursor и набрать `/opsx` — команды должны появиться в автодополнении.

## 3. Change: артефакты и цикл

**Change** — единица работы в OpenSpec: папка `openspec/changes/<change-name>/`, в которой изменение живёт от постановки до архивации. Внутри четыре артефакта, и у каждого свой вопрос.

Структура change (пример с 2FA):

```text
openspec/changes/add-2fa/
├── proposal.md      # зачем: мотивация и границы change
├── specs/           # что меняется: дельта требований
├── design.md        # как реализуем: архитектура и взаимодействие
└── tasks.md         # в каком порядке: последовательность работ
```

### 3.1 Четыре артефакта

На ревью читать их в этом порядке:

| Файл | Вопрос | Что внутри |
| --- | --- | --- |
| **`proposal.md`** | Зачем? | Мотивация и границы change. Без деталей реализации. |
| **`specs/`** | Что меняется? | Дельта: добавленные, изменённые и удалённые требования. **Не копия всей спецификации.** |
| **`design.md`** | Как реализуем? | Архитектура, хранение данных, взаимодействие сервисов. |
| **`tasks.md`** | В каком порядке? | Последовательность работ. По нему идёт `apply`, отмечая `[x]`. |

`design.md` **обязателен**: схема `spec-driven` считает его зависимостью для `tasks`. Без файла tasks останется заблокированным, поэтому его создают даже для простого change — достаточно короткой заметки. **Если требование нельзя проверить сценарием, оно ещё не готово для spec.**

### 3.2 Минимальный фрагмент delta

```text
## ADDED Requirements
### Requirement: Код подтверждения действует 10 минут
Система SHALL отклонять код старше 10 минут.
#### Scenario: Пользователь ввёл просроченный код
- WHEN пользователь вводит код старше 10 минут
- THEN система показывает ошибку и предлагает запросить новый код
```

Требование сформулировано как проверяемое поведение. Сценарий задаёт условие и ожидаемый результат. Такая запись одинаково понятна разработчику, QA и агенту: не нужно угадывать, что значит «код должен вовремя истекать».

### 3.3 Цикл работы

| Шаг | Что происходит | Что остаётся |
| --- | --- | --- |
| `propose` | Собирает change: требования, сценарии и задачи | Артефакты в `openspec/changes/` |
| `apply` | Идёт по `tasks.md` и пишет код | Код и отметки `[x]` |
| `archive` | Вливает дельту в `openspec/specs/` | Спека с новым поведением, change в архиве |

После `archive` spec описывает **текущее поведение системы**. Следующий change будет менять уже её, а не начинать с чистого листа.

В Claude Code эти шаги — `/opsx:propose`, `/opsx:apply` и `/opsx:archive`. В OpenCode и Cursor — `/opsx-propose`, `/opsx-apply` и `/opsx-archive`.

### 3.4 Что проверяется

- **Проверяемость требования.** У каждого требования есть сценарий с условием (WHEN) и ожидаемым результатом (THEN); иначе требование не готово для spec.
- **Наличие `design.md`.** Без него `tasks` заблокирован схемой `spec-driven`.
- **Полнота дельты.** В `specs/` — только изменения (добавленные, изменённые, удалённые требования), а не копия всей спеки.
- **Задачи и прогресс.** `tasks.md` — последовательность работ; `apply` отмечает выполненные пункты `[x]`.
- **Валидация и статус.** `openspec validate <change>` проверяет change, `openspec status --change <change>` показывает прогресс.

Чек-лист готового change (собран из требований выше): все четыре артефакта на месте, у требований есть сценарии, `design.md` заполнен, все задачи `tasks.md` отмечены `[x]`, `validate` не даёт замечаний — после этого `archive` переносит дельту в spec.

### 3.5 Пример с 2FA

В spec для двухфакторной аутентификации могут попасть четыре требования. В `tasks.md` они разворачиваются в работы:

| Требование | Задача |
| --- | --- |
| Код действует 10 минут; старше — отклоняется | Хранить код с TTL и проверять срок |
| Повторная отправка не чаще раза в 60 секунд; новый код отменяет предыдущий | Ограничить отправку и отменять предыдущий код |
| После пяти неверных попыток ввод блокируется на 15 минут | Добавить блокировку после серии ошибок |
| При потере телефона доступ восстанавливается через поддержку | Описать и реализовать сценарий восстановления |

Полный код здесь не нужен. Каждое требование имеет сценарий, а каждая задача ведёт к проверяемому результату. Если десять минут окажутся неверным значением, меняется **spec и сценарий**, а не только константа в коде. После `archive` правило останется в `openspec/specs/` и станет основой для ручных проверок и автотестов — поэтому **QA подключается до реализации**.

## 4. Команды `/opsx-*`

Команды `/opsx-*` работают в поле ввода агента: Claude Code, OpenCode или Cursor. В системной оболочке (shell) их нет — там работает `openspec ...`.

| Где | Что вводить | Что происходит |
| --- | --- | --- |
| Поле ввода агента | `/opsx:propose` (Claude) или `/opsx-propose` (OpenCode, Cursor) | Агент создаёт и меняет артефакты, может писать код |
| Shell | `openspec status`, `openspec list`, `openspec validate` | CLI читает состояние проекта и показывает его |

Change один и тот же: файлы лежат в `openspec/changes/`, и обе стороны видят их. **Команда агента меняет план, CLI помогает его проверить.**

### 4.1 Основной набор

Шесть команд закрывают цикл от идеи до архива.

| Команда | Что делает | Когда использовать |
| --- | --- | --- |
| `/opsx:explore` | Изучает код и варианты, код не пишет | Задача ещё не сформулирована |
| `/opsx:propose` | Создаёт change и артефакты планирования | Понятно, что нужно сделать |
| `/opsx:apply` | Идёт по `tasks.md`, пишет код и отмечает задачи | План готов и проверен |
| `/opsx:update` | Правит существующие артефакты, код не трогает | Изменились требования |
| `/opsx:sync` | Вливает дельты в `openspec/specs/` без архивации | Спеки нужны раньше завершения |
| `/opsx:archive` | Синхронизирует дельты и переносит change в архив | Работа завершена |

**Типичный порядок:** `explore` → `propose` → `apply` → `archive`. `update` и `sync` встают между шагами по необходимости.

В OpenCode и Cursor те же команды пишутся через дефис: `/opsx-explore`, `/opsx-propose`, `/opsx-apply` и так далее.

### 4.2 Расширенный набор

| Команда | Что делает |
| --- | --- |
| `/opsx:new` | Создаёт только каркас change |
| `/opsx:continue` | Создаёт следующий артефакт по зависимостям |
| `/opsx:ff` | Fast-forward: все артефакты сразу |
| `/opsx:verify` | Сверяет реализацию с артефактами |
| `/opsx:bulk-archive` | Архивирует несколько changes |
| `/opsx:onboard` | Прогоняет полный цикл на вашем коде |

Нюансы выбора:

- `ff` быстрее, но ошибка в `proposal.md` тянет за собой остальные файлы;
- `new` + `continue` дают тот же результат с остановками для ревью: на задаче с открытыми вопросами это дешевле;
- `verify` полезен перед архивацией, `bulk-archive` — когда накопилась очередь, `onboard` — чтобы увидеть цикл на знакомом репозитории.

### 4.3 Профиль workflow

```bash
openspec config profile
openspec update
```

Первая команда меняет настройку, вторая переносит её в проект. Запускать **обе в shell**, не в поле ввода агента.

Правило разделителя работает для всего набора, включая `new`, `continue`, `ff`, `verify`, `bulk-archive` и `onboard`. Смотреть на приглашение перед вводом: строка shell ждёт `openspec`, поле ввода агента — `/opsx-*`; при перепутанном разделителе агент не находит команду и отвечает обычным текстом.

### 4.4 Проверка состояния из CLI

| Задача | Команда |
| --- | --- |
| Прогресс change | `openspec status --change add-2fa` |
| Очередь changes | `openspec list --changes` |
| Текущие specs | `openspec list --specs` |
| Архив | `openspec list --archived` |
| Содержимое change | `openspec show add-2fa` |
| Валидация | `openspec validate add-2fa` |
| Архивация из CLI | `openspec archive add-2fa --yes` |

CLI не меняет план: он показывает фактическое состояние. Удобно для ревью и для возврата в контекст, когда чат закрыт.

### 4.5 Флаги и параметры

| Флаг | Где встречается | Смысл |
| --- | --- | --- |
| `--tools claude,opencode,cursor` | `openspec init` | Набор инструментов без диалога (скрипты, CI, повторная инициализация) |
| `--no-animation` | `openspec init` | Убирает анимацию приветствия (скриншоты, логи CI) |
| `--change <name>` | `openspec status` | Указать change для просмотра прогресса |
| `--changes` / `--specs` / `--archived` | `openspec list` | Что показывать: changes, specs или архив |
| `--yes` | `openspec archive`, `openspec store remove` | Подтвердить действие без запроса |
| `--store <id>` | Команды work со specs и changes | Явно выбрать store; перекрывает настройки из конфигов |
| `--json` | `openspec store list` | Машиночитаемый вывод для агента |
| `--path <dir>` | `openspec store setup` | Локальная папка store |
| `--remote <url>` | `openspec store setup` | Записать адрес удалённого репозитория в `store.yaml` |
| `--no-init-git` | `openspec store setup` | Не делать `git init` и первый коммит |

## 5. Stores (beta)

> **Beta.** Функция в статусе beta: имена команд, флаги, форматы файлов и JSON могут меняться.

### 5.1 Сценарий: одна фича в трёх репозиториях

Фича «оплата подписки» затрагивает backend, web и мобильное приложение. У каждого репозитория свой `openspec/` и свои changes. Общий контракт удобнее держать в одном месте: backend, web и mobile читают specs store, а не пересказывают их друг другу.

### 5.2 Что такое store

**Store** — отдельный git-репозиторий, который существует только для планирования. Внутри та же структура `openspec/`, что и в обычном проекте, плюс файл идентичности `.openspec-store/store.yaml`. **Кода приложения в store нет**: его не собирают, не деплоят и не подключают как зависимость. Кодовые репозитории ссылаются на store.

Store отделяет план от реализации: общий контракт живёт в одном месте, реализация — в своих репозиториях. Один store обслуживает сколько угодно репозиториев: backend, web, мобильный клиент, инфраструктуру. Id и границы store команда выбирает сама. **Регистрация привязана к машине**: на каждом рабочем месте store регистрируется отдельно.

`references` даёт доступ к **specs store, а не к активным changes**. Если контракт ещё лежит в change, его читают явно: `openspec show <change> --store <id>`. Синхронизация store — обычный git.

### 5.3 Создать store

```bash
openspec store setup team-plans --path ~/openspec/team-plans
```

`team-plans` здесь — id store, `--path` — локальная папка. `setup` создаёт store и **регистрирует его на машине**, поэтому дальше достаточно id: путь искать не нужно.

По умолчанию `setup` делает `git init` и первый коммит. Если git не знает `user.name` и `user.email`, настроить их заранее или использовать `--no-init-git`.

С удалённым репозиторием:

```bash
openspec store setup team-plans --path ~/openspec/team-plans \
  --remote https://git.rnd.mtt/oliwio/.../repo/team-plans.git
```

`--remote` **только записывает адрес в `store.yaml`**. Он не создаёт проект в GitLab, не клонирует и не делает push. В примере `...` — сокращение: заменить на полный путь группы.

Создать пустой проект в GitLab, затем отправить store:

```bash
cd ~/openspec/team-plans
git remote add origin https://git.rnd.mtt/oliwio/.../repo/team-plans.git
git push -u origin HEAD
```

Коллега клонирует репозиторий и регистрирует его:

```bash
git clone https://git.rnd.mtt/oliwio/.../repo/team-plans.git ~/openspec/team-plans
openspec store register ~/openspec/team-plans
```

### 5.4 Структура store

```text
team-plans/                      # отдельный git-репозиторий
├── .openspec-store/
│   └── store.yaml               # идентичность store (обязателен)
├── openspec/
│   ├── specs/                   # общие спеки
│   ├── changes/                 # активные changes
│   │   └── archive/             # завершённые changes после архивации
│   └── config.yaml              # настройки store
└── .git/
```

`store.yaml`:

```yaml
version: 1
id: team-plans
remote: https://git.rnd.mtt/oliwio/.../repo/team-plans.git
```

`remote` необязателен. **Коммитить `store.yaml` вместе с остальным store**: идентичность должна ехать вместе с планом, иначе на другой машине store зарегистрируется под другим путём или без remote.

### 5.5 Управление store

```bash
openspec store list
openspec store ls
openspec store unregister team-plans
openspec store remove team-plans --yes
openspec store doctor team-plans
```

- Сверять id по выводу `list` или `ls` перед запуском команд.
- `unregister` убирает регистрацию, **папку не трогает**: файлы остаются на диске, store можно зарегистрировать снова.
- `remove` удаляет **и регистрацию, и папку** — проверить, что нужный change уже запушен.
- `doctor` проверяет состояние и **ничего не чинит**: вывод читать как диагностику, правки вносить руками.

### 5.6 Работа с change в store

```bash
openspec new change add-subscription --store team-plans
openspec status --change add-subscription --store team-plans
openspec validate add-subscription --store team-plans
openspec archive add-subscription --store team-plans --yes
```

Команды работы со specs и changes принимают `--store`. Флаг ставится **в каждой команде**: он выбирает store явно и перекрывает настройки из конфигов. `status` и `validate` читают change и ничего не меняют; `archive` завершает change и переносит его дельты в общие specs store.

### 5.7 Slash-команды

Отдельных `/opsx:store-*` нет. `/opsx:propose`, `/opsx:apply`, `/opsx:archive` работают с store, если **назвать store в запросе**. Агент вызывает `openspec store list --json`, находит id и дальше подставляет `--store <id>`.

Claude Code:

```text
/opsx:propose add-subscription в store team-plans
```

OpenCode и Cursor:

```text
/opsx-propose add-subscription в store team-plans
```

Называть store так, как он записан в `id` внутри `store.yaml`. Если store в запросе не назван, команда идёт по локальному `openspec/`, когда он есть.

### 5.8 Подключить кодовый репозиторий

В `openspec/config.yaml` кодового репозитория:

```yaml
references:
  - team-plans
```

`references` даёт агенту **read-only контекст**: он видит specs из store и открывает их через `openspec show <spec> --store team-plans`. **Записывать в store из кодового репозитория нельзя**: план меняется только в самом store. `references` не заменяет локальный `openspec/` — репозиторий может держать свои specs и одновременно читать store.

Если весь проект должен по умолчанию работать со store:

```yaml
store: team-plans
```

Это работает, **только если в репозитории нет локальных** `openspec/specs/` и `openspec/changes/`. После `openspec init` локальный `openspec/` уже создан, поэтому `store:` не переключит команды. Для такого репозитория оставить `references` или указывать `--store` явно.

Глобальный fallback для машины:

```bash
openspec config set defaultStore team-plans
```

### 5.9 Приоритет выбора root

1. `--store <id>` в команде.
2. Локальный `openspec/` в текущем репозитории.
3. `store:` в `openspec/config.yaml`.
4. `defaultStore` в глобальном конфиге.

В репозитории с локальным `openspec/` и `store: team-plans` команда без флага пойдёт по локальному каталогу — настройка **молча не сработает**. В скриптах указывать `--store`.

### 5.10 Рабочий процесс команды (пример на трёх репозиториях)

1. Вести планирование в `team-plans`: один change с общими требованиями и контрактом.
2. Когда контракт готов, выполнить `/opsx:sync` или `/opsx:archive` в store — дельта попадёт в `openspec/specs/`.
3. В backend и web добавить `references: [team-plans]`. Теперь они видят specs store.
4. Пока change ещё активен, читать его явно: `openspec show <change> --store team-plans`.
5. Запускать `/opsx:apply` отдельно в каждом кодовом репозитории.

Change в store держит общий контракт, кодовые changes описывают реализацию. Правку контракта видит вся команда в одном репозитории, на ревью плана.

**Чего Stores не делает:** не роутит задачи по репозиториям (агент видит код только тех папок, которые открыты) и не держит несколько checkout одного store на машине — один store id, один локальный путь.
